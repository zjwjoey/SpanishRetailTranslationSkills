# SpanishRetailTranslationSkills — 翻译 Skills 竞争进化与淘汰计划 V1

## 一、项目背景与任务定位

项目仓库：

https://github.com/zjwjoey/SpanishRetailTranslationSkills.git

你现在担任本项目的首席研发工程师、翻译质量评测负责人及 Skills 架构优化负责人。

本次任务不是简单增加术语、补充提示词，也不是继续无限量翻译 SKU。

**核心目标：建立一套能够研究 GitHub 开源翻译能力、利用真实商品数据进行规则训练、通过公平竞争持续优化与淘汰 Skills 的研发体系。**

最终留下的 Skills 必须在翻译准确性、关键信息保留、专业术语、人工返工及执行成本等方面体现实际价值。

现有五个 Skills 不是固定资产，可以保留、重构、合并、替换、停用或淘汰。

本次所称“训练”，是对 Skill 指令、规则、术语库、工作流及评测机制的持续优化，不涉及大语言模型权重训练或微调。

## 三、GitHub 资料与数据研究

首先审查三个上游仓库的最新代码、README、SKILL.md、references、测试程序、示例及许可证。

此外，允许研究其他公开 GitHub 仓库中与以下内容有关的资料：

1. 西班牙语与简体中文商品翻译。
2. 零售商品分类及多义词术语库。
3. 家居、五金、电子、厨房、清洁及日用品术语。
4. 型号、规格、单位、包装数量和兼容清单保护。
5. 翻译质量评估、反虚构、漏译检测。
6. 合法公开的商品双语对照数据和人工纠错案例。

每一项新增外部资料必须记录：

- GitHub 仓库地址与固定 commit。
- 数据来源、语言方向和适用领域。
- LICENSE 与可复用范围。
- 实际文件路径及 SHA256。
- 是否经过人工核验。
- 用途：训练、验证参考、工程案例或不可使用。

GitHub 上的译文不能因公开就自动认定为正确答案。

不能将未经验证的双语材料直接升级为可信术语，也不能擅自重新发布许可证不允许的数据。

如果没有找到足够可靠的外部商品双语数据，就用 GitHub 资料研究方法和规则，使用本机已有真实商品源作为实验数据，不得伪造外部训练集。

## 四、数据管理与训练方式

现有真实商品来源：

- Action 西班牙站。
- Amazon.es。
- IKEA 西班牙站。

优先使用现有采集系统已经产生的原始西语商品数据。

不得修改 ActionSKUTracker、AmazonESBestseller、IKEASKUTracker 的采集程序、生产数据库或原始文件。

### 1. 先清点历史曝光数据

识别过去所有已用于生成、规则优化、人工或 AI 核对的商品，包括：

- Action 历史测试商品。
- Amazon 第一轮、第二轮和第三轮商品。
- IKEA 两批商品。
- 前期独立对照使用的商品。
- 已知失败案例、返工商品和备用候选。

按稳定 SKU、ASIN、Parent ASIN、变体、系列、同款及近重复关系去重。

不能将此前训练过的商品重新称为全新盲测样本。

### 2. 采用统一的数据划分

第一阶段建议建立 120 个全新真实商品的试验池：

| 用途 | Action | Amazon | IKEA | 合计 |
|---|---:|---:|---:|---:|
| 训练集 | 20 | 20 | 20 | 60 |
| 验证集 | 12 | 12 | 12 | 36 |
| 最终测试集 | 8 | 8 | 8 | 24 |
| 合计 | 40 | 40 | 40 | 120 |

每个平台同时覆盖普通商品和复杂商品，并尽量分散类目。

此数量是首轮工程实验目标，不是强行凑数指标。若可用且可证明未曝光的数据不足，应减少规模并说明缺口。

样本选择及分组在生成译文前冻结。训练、验证、最终测试的同款关系组不得交叉。

正式标准答案必须由可信人工按字段确认。没有人工确认的数据可以用于工程诊断和候选优化，但不能称为人工金标准。

最终测试集在所有候选版本冻结前不得开放给训练者或优化者。

### 3. 多方案使用完全相同的训练集

各参赛方案使用相同的原始西语商品、相同的人工作业反馈、相同验证集和统一输出要求。

各方案独立优化，不允许读取其他方案的输出或评测答案。

不得因为某个候选已经出现问题，就额外给予它更多已确认答案、重试机会或人工帮助。

不同方案可以拥有不同工作流程，但资源差异必须记录，避免将额外算力或额外提示词误认为 Skill 自身收益。

## 五、竞争训练机制

整个训练与评测采用以下结构：

```text
统一西语商品数据
        │
        ▼
独立候选环境
        │
        ├── 普通 Codex 基线
        ├── 专业提示词基线
        ├── 当前五 Skills 基线
        ├── GitHub 项目 A 候选
        ├── GitHub 项目 B 适配候选
        └── GitHub 项目 C 专项或完整候选
        │
        ▼
同一训练集分别优化
        │
        ▼
同一验证集配对比较
        │
        ▼
保留有效改进
        │
        ▼
合并、精简、替换或停用无效能力
        │
        ▼
冻结最终候选版本
        │
        ▼
独立新商品测试
```

### 第一轮：原始能力测试

在尚未针对本次数据进行优化时，先冻结所有可运行候选。

使用少量相同的开发样本验证：

- Skill 是否真实触发。
- SKILL.md 和必要 references 是否被实际读取。
- 是否输出完整真实中文，而不是模板或原文回显。
- 品牌、型号、数量和规格是否保存。
- 是否存在明显漏译或虚构。
- 是否能批量处理。

不能原生运行的项目先进行明确范围的适配，但保留未经适配的原始版本作为证据。

不得把适配过程中针对商品的额外优化冒充原生能力。

### 第二轮：规则训练

各候选使用相同训练数据。

通过已确认的纠错案例优化：

- 翻译规则。
- 术语与上下文判断。
- 材质、部件、数量角色。
- 兼容对象和条件。
- 长字段筛选。
- 不确定事实局部隔离。
- 翻译审查机制。

每次优化必须记录：

`发现问题 → 原始证据 → 根因 → 修改内容 → 回归结果 → 新数据验证`

同一失败案例的修复只能证明该案例恢复，不能证明泛化能力提升。

每轮主要优化必须在独立验证集上比较，最多先安排三轮主要训练优化。不能为了得到想要的排名无限重跑。

### 第三轮：技能组合实验

在完整候选方案比较之外，对当前五个 Skills 进行逐项停用和组合实验。

例如：

- 去掉 Category，检查分类与术语质量是否下降。
- 将 Category 合并到 Translator，检查是否能减少成本。
- 去掉独立 Terminology，检查专业错译和型号损坏是否增加。
- 有无 Reviewer，比较漏译检出、误报率与额外耗时。
- 将 Learning 改为离线优化程序，检查是否无需保留独立运行 Skill。

每次只改变一个主要能力，其他环境保持一致。

对有潜力的组合进行相同验证，不允许用旧训练样本反复证明新版本优越。

## 六、统一评分标准

不得只使用一个模型自动打分来宣布胜出。

使用独立、盲化、先源事实后中文候选的审核方式。重要分歧要人工复核。

| 维度 | 优先级 |
|---|---|
| 商品主体和关键配置准确性 | 最高 |
| 重要事实遗漏及虚构 | 最高 |
| 规格、数量、尺寸、单位、型号与兼容信息 | 最高 |
| 材质、部件、专业术语与限制条件 | 高 |
| 实际人工返工次数和时间 | 高 |
| Token、耗时与实际费用 | 中 |
| 中文零售表达自然度和格式 | 中 |

错误级别：

- P0：身份、主体、关键配置错误，重大事实虚构或误删。
- P1：重要属性、术语、兼容对象、用途或限制条件错译或遗漏。
- P2：不影响商品事实的表达、格式、一般结构问题。

AI 原始审查意见不直接计入已确认错误。

源文问题、审查误报、人工确认错误分别记录。

对同一源事实在多个目标字段出现的问题，只统计一个根因，但记录全部受影响字段。

### 胜出判断

主要依据是相比专业提示词基线及现有五 Skills 的增量收益。

不得仅以 P2 数量下降就宣布翻译质量升级。

必须同时考察：

1. 是否出现新增 P0 或重大 P1 回归。
2. 复杂商品关键事实覆盖是否改善。
3. 是否减少可证的实际人工返工。
4. 是否在质量不下降的条件下降低 Token 和耗时。
5. 是否能在不同类目及新商品上重复表现。

如没有人工金标准，报告 AI 工程性观察和未决风险，不输出正式准确率或人工返工率。

### 淘汰机制

候选能力不因为一次小样本排名靠后就永久删除。

如果某项独立能力在至少两次不重叠的新商品验证中，均没有可证增益，且造成明显额外复杂度或资源开销，应进入：

`保留观察 → 停用候选 → 组合验证 → 冻结归档`

在质量不下降的情况下，可把其有效规则合并至其他 Skill。

需要回退的版本必须完整保留。

## 八、Codex 子智能体安排

由主智能体统一负责实验设计、数据冻结、任务调度、阶段验收和版本管理。

建议安排：

- GitHub 研究智能体：研究外部仓库、许可证、真实实现与可用数据。
- 候选适配智能体：在独立工作区完成各上游项目的 Codex 适配。
- 数据智能体：处理来源、历史曝光去重、分层抽样、数据冻结。
- 翻译实验智能体：执行各独立候选，不能读取其他组答案。
- 独立 QA 智能体：先从原文建立事实清单，再盲化审查译文。
- 架构优化智能体：根据确认结果提出合并、精简和淘汰建议。

同一个子智能体不得同时担任对应商品的生成者和独立审校者。

共享 Skills、统一契约和评测规则只能由主智能体在明确阶段串行维护，避免多个子智能体同时改动同一文件。

并行度根据实际吞吐、上下文容量和质量决定，不固定给每个 SKU 启动多个子智能体。

## 九、运行和 CI 策略

本项目以实际翻译质量为主，避免频繁运行成本很高的完整 CI。

采用分级验证：

- 每次小修改：只执行对应 Skill 的快速结构检查及少量失败案例回归。
- 每轮规则冻结：执行专项与跨 Skill 回归，核查身份、哈希和输出结构。
- 每轮独立比较：执行真实候选生成与独立 QA。
- 最终发布前：完整测试与必要 CI 验收。

测试未实际运行必须标记 `NOT_RUN`，不允许以历史 CI 通过冒充当前版本通过。

重点记录生成、审查和读取 Skills 的真实 Token 与耗时，排除无意义的重复全文载入。

## 十、自动推进与终止条件

收到本任务后直接进入研发执行，不要只输出设计文档或要求我逐阶段批准。

优先顺序：

1. 审计当前仓库状态和已有评测证据。
2. 核验 GitHub 三个上游项目和许可证。
3. 建立隔离开发分支。
4. 审查 Codex 原生 Skill 发现与读取是否可用。
5. 盘点历史曝光数据，冻结试验样本。
6. 验证各候选真实可运行性。
7. 执行首轮同条件基线实验。
8. 进行训练集驱动的候选优化。
9. 完成验证集竞争和五 Skills 逐项停用实验。
10. 冻结优胜候选后进行独立最终测试。
11. 整理保留、合并、淘汰建议与下一版本架构。

依赖前一步实际证据的阶段，不得在门槛未通过时继续假装完成。

如果数据不足、原生加载不可用、人工验证缺失或许可证不允许，停止受影响的路线，保留失败证据，同时继续其他独立可执行工作。

不要通过造数据、使用历史曝光商品冒充新样本、减少审查范围、改变评分口径或重新选择容易商品来制造提升。

对于质量相当的方案，优先选择规则更少、加载更轻、维护成本更低的实现。
